PROBLEMS THAT ARE SOLVED WITH THIS PROJECT
    1. Idempotency: "Never Charge Twice"
    The Problem
    Imagine a customer on a mobile phone clicking "Pay $100".

    The request reaches your server, and your database deducts $100.
    The server tries to send back 200 OK, but right at that millisecond, the customer goes through a tunnel and loses Wi-Fi.
    The mobile app times out and automatically retries the request (or the user taps "Pay" again).
    Without protection, your server treats this as a brand-new payment and deducts another $100. The customer is furious.
    How It Works
    An operation is idempotent if performing it once or performing it 10 times produces the exact same end state.

    Idempotency Key: A unique UUID generated by the client for that specific payment attempt.
    If the server sees a key it has already processed, it does not run business logic again—it immediately returns the saved response.  

    2. Optimistic Locking & Retries: "Preventing Lost Updates"
    The Problem (The Lost Update Anomaly)
    Suppose Alice and Bob share an account with a $100 balance. At the exact same second:

    Alice spends $30 at a grocery store (Thread A).
    Bob spends $40 at a gas station (Thread B).
    Here is what happens without concurrency control:

    Thread A reads balance: 100.
    Thread B reads balance: 100.
    Thread A calculates 100 - 30 = 70 and writes balance = 70.
    Thread B calculates 100 - 40 = 60 and writes balance = 60.
    Result: The balance is $60, but $70 was spent! The bank just lost $30 because Thread B overwrote Thread A's update.

    How Optimistic Locking Solves It
    Instead of locking the entire row upfront (which hurts performance), we add a version column to the Account table:

        UPDATE account 
        SET balance = 70, version = version + 1 
        WHERE id = 1 AND version = 1;

    Thread A updates first: DB finds version = 1, sets balance = 70, version = 2. (Success!)
    Thread B tries to update with WHERE version = 1: DB updates 0 rows because the version is already 2.
    JPA detects 0 rows updated and throws an OptimisticLockException.

    Why We Need Spring Retry
    Thread B shouldn't just crash and tell Bob his payment failed. With Spring Retry (@Retryable), Thread B automatically catches the exception, re-reads the fresh balance ($70, version = 2), calculates 70 - 40 = $30, and successfully saves it with version = 3.

    3. The Outbox Pattern: "Atomic State + Eventual Notification"
    The Problem (The Dual-Write Dilemma)
    When a transaction succeeds, you need to do two things:

    Save the transaction to your PostgreSQL database.
    Notify an external system (e.g., send a webhook to the Payment Service Provider / PSP).
    What if you do this in one @Transactional method?

        @Transactional
    public void processPayment() {
     accountRepository.save(account);      // Step 1: DB write
     pspClient.notifyExternalPSP(payment); // Step 2: HTTP call
    }

    If the external HTTP call is slow (5 seconds), your database connection is held open for 5 seconds (exhausts your DB connection pool!).
    If the external call succeeds, but the DB transaction fails to commit right after, you notified the external system for a payment that was rolled back!
    If the DB commits, but the server crashes before the HTTP call, the external system is never notified.


    How the Outbox Pattern Solves It
    You do not make network calls inside a database transaction. Instead:

        [ POST /pay Request ]
          |
           v
       (Single DB Transaction)
    +------------------------------------+
    | 1. Update Account Balance          |
    | 2. Insert Transaction Record       |
    | 3. Insert Outbox Record (PENDING)  |
    +------------------------------------+
          |
          v (Commit & Return 200 OK immediately)

    [ Background @Scheduled Worker (every 5s) ]
          |
         |--> Reads PENDING outbox records from DB
        |--> Calls Mock External PSP API over HTTP
           |--> Marks Outbox Record as SENT


    4. Reconciliation Engine: "Trust, but Verify"
    The Problem
    In financial systems, bugs happen, network timeouts happen, and third-party fees occur. At the end of the day, how do you know your database matches the actual money moved at the bank or PSP?

    How It Works
    Every night, payment processors (like Stripe, Adyen, Visa) produce a settlement report (usually a CSV file) of all transactions they processed.

    Your Reconciliation Job:

    Sums and groups all transactions recorded in your internal DB for that day.
    Parses the external PSP's CSV file.
    Compares them row-by-row and aggregate-by-aggregate:
    Did we record a transaction the PSP doesn't have? (Ghost transaction)
    Did the PSP record a transaction we missed? (Missing transaction)
    Do the amounts match?
    Any mismatch is recorded in a reconciliation_errors table for human investigation.

Controller -> Handles HTTP Routing, headers, JSON parsing, input validation, response codes

Service -> A layer of abstraction between the controller and the repo, contains business rules, manages database transactions (@Transactional), orchestrates retries (@Retryable), and calls the Outbox.

Repository -> Communicates with database, SQL queries etc.

DTO (Data Transfer Object) : We use this to not expose our entire entities to users so that we don't give hackers each attribute, they could do an Over-Posting attack.

DAO (Data Access Object): Design pattern, object that we use to access data, in our case it is the repositories that implement JPA.


JPA (Jakarta Persistence API) is the specification (the blueprint/rules). It defines annotations like @Entity, @Table, @Id, @Version, and the EntityManager interface, but contains no actual database execution code.
Hibernate is the actual implementation (the engine under the hood).
Object-Relational Mapping (ORM): Reads our @Entity classes and converts Java objects into SQL queries (SELECT, INSERT, UPDATE, DELETE).
Dirty Checking: When you modify an entity inside a @Transactional method (e.g. account.debit(50)), Hibernate tracks that the balance field changed and automatically writes the UPDATE SQL when the transaction commits.
Caching & Concurrency: Handles optimistic locking checks (@Version) and first-level caching.

Does JPA .save() Only Work With PostgreSQL? How Do We Adapt to Other DBs?
No, JPA .save() works with virtually any relational database (PostgreSQL, MySQL, Oracle, SQL Server, SQLite, H2, MariaDB, etc.).

Your Java code (Account.java, AccountRepository.java, AccountService.java) does not change by a single line of code.

How Hibernate Adapts Behind the Scenes:
Hibernate uses something called a Database Dialect.

In PostgreSQL, an identity column uses BIGSERIAL / GENERATED ALWAYS AS IDENTITY.
In MySQL, it uses AUTO_INCREMENT.
In Oracle, it uses a SEQUENCE.
When you call accountRepository.save(account), Hibernate checks its configured Dialect and generates the exact SQL flavor required by that specific database.

 How Does GlobalExceptionHandler Work?
Without a Global Exception Handler, if your code throws throw new AccountNotFoundException(...), the exception bubbles all the way up to the web server (Tomcat), resulting in an ugly 500 Internal Server Error with a 100-line stack trace leaked to the user.

Here is how Spring handles exceptions with @RestControllerAdvice:
[ Client Request: GET /api/v1/accounts/999 ]
                    |
                    v
             [ Controller ]
                    |
                    v
              [ Service ] ----> Throws AccountNotFoundException("Account 999 not found")
                    |
                    x (Spring intercepts the exception before it leaves the app)
                    v
       [ GlobalExceptionHandler (@RestControllerAdvice) ]
                    |
                    |--> Matches @ExceptionHandler(AccountNotFoundException.class)
                    |--> Constructs ErrorResponse DTO (status: 404, message: "Account 999 not found")
                    v
[ Client gets clean JSON: 404 NOT FOUND ]


ACID = 
Atomicity : Either every single operation in the transaction succeeds, or the entire transaction is rolled back.
Consistency : Rules are never broken. The database always moves from one valid state to another, strictly enforcing all database rules, foreign keys, unique constraints, and @Version numbers.
Isolation : No stepping on each other's toes. Multiple transactions running at the exact same millisecond cannot see each other’s intermediate/unfinished state.
Durability : Survives power outages. Once a transaction commits (COMMIT), the data is written to disk/WAL log permanently. Even if lightning strikes the server 1ms later, the money transfer is saved.

AAA Pattern (For integration testing):

1. ARRANGE (Given)  ──> Set up test data (e.g. create Account 1 with $100, Account 2 with $50)
2. ACT     (When)   ──> Perform the operation (e.g. transfer $30 from Account 1 to Account 2)
3. ASSERT  (Then)   ──> Verify the result (e.g. check Account 1 has $70, Account 2 has $80, ledger record created)
